# Архитектура и сверка с исходным кейсом

Версия 1.2, 11 октября 2026. Основание: исходное техническое задание ФСП «Цифровая платформа-агрегатор ИТ-вакансий…», разделы 2.1–3.5. Собственное расширенное ТЗ проекта не подменяет требования организатора.

## Результат аудита

Основная механика кейса реализована сквозным сценарием: кандидат заполняет профиль, выбирает уровень, сдаёт индивидуальный вариант теста, получает категорию; компания создаёт потребность, находит кандидата и предлагает зарплату; контакт раскрывается после адресного согласия. Дополнительные сценарии вакансий, откликов, практики и PDF работают.

Есть одно сознательное расхождение с обязательным пунктом 2.2.4: почтовое подтверждение отключено по решению команды. Код верификации и тесты остаются, режим включается EMAIL_VERIFICATION_REQUIRED=true при настроенном SMTP. Cloudflare обеспечивает HTTPS и доступность маршрута, но не подтверждает владение почтой. Для буквального соответствия этому пункту перед сдачей нужен реальный почтовый провайдер и включение режима либо согласованное исключение организатора.

Нельзя считать научно подтверждёнными профессиональные грейды или эффективность реального найма. Организатор допускает собственную синтетику; её происхождение и ограничения явно описаны. Официальный API ФСП не предоставлен самим организатором, поэтому демонстрационный реестр соответствует допустимому формату хакатона, но не является подключением к реальному реестру.

| Интерфейс | Маршруты, формы, сценарии двух ролей | Next.js App Router, React, shadcn/Radix, Manrope |
| Оболочка кабинета | Сессия, навигация, меню аккаунта | app/app/layout.tsx, views/product/dashboard.tsx |

| Практика | Каталог, фильтры статуса, черновик, отправка и проверка | views/product/challenges.tsx; отдельная лениво загружаемая WebGL-сцена |
| API | Проверка роли, владение, переходы состояний | backend/main.py, security.py, schemas.py |
| Контракт | Запросы, DTO ответов, cookie, ошибки | backend/api_contract.py, /api/v1/openapi.json |
| Категории | Единые стабильные ID направлений | backend/taxonomy.py; frontend/src/lib/taxonomy.json, тест синхронизации |
| Проверка навыков | Неизменяемый вариант, таймер, проверка ответов | assessment.py и assessment_tracks.py, банк 2.0 |
| Подбор | Жёсткий фильтр категории, признаки, формула и модель | matching.py, ml/model.json |
| Представление данных | Удаление контактов из выдачи до согласия | serializers.py; проверка ContactGrant |
| PDF | Извлечение редактируемого черновика, экспорт профиля | resume.py, pdf_export.py |
| Данные | Связи, уникальность, транзакции, аудит | SQLAlchemy, PostgreSQL 17; SQLite только локально/в тестах |
| Набор комиссии | Идемпотентные вымышленные сценарии | judge_catalog.py поверх базовых seed/catalog |

Это модульный монолит с отдельным веб-приложением. Отдельные микросервисы и распределённая очередь не нужны для проверки основной механики и не заявляются как реализованные. Модель работает локально на CPU, внешняя LLM не получает резюме. Доменные данные не хранятся в браузере; localStorage содержит состояние меню, избранное и черновик практики, привязанные к ID пользователя. Сессионный токен доступен только через HttpOnly-cookie.

### Ключевые инварианты

- Специализация и подтверждённый грейд задают одну категорию. Сохранение профиля не может произвольно поменять подтверждённую специализацию.
- Профиль попадает в банк только с согласием, публикацией и подтверждённым грейдом. Достижения ФСП не заменяют тест.
- ContactGrant уникален для пары компания–кандидат. Приглашение без принятия не выдаёт контакт; отзыв доступа применяется при следующем чтении API.
- Публикация вакансии и приглашение требуют диапазон зарплаты. Отклик и решение практики защищены от дублей уникальными ограничениями БД.
- Состояние попытки, ответы и срок хранятся на сервере. Перезагрузка браузера не обнуляет таймер. Неудача сохраняет уже подтверждённый грейд.
- Начальные данные не обновляют пользовательские правки. Повтор seed не воссоздаёт отозванные согласия.

| Воспроизводимость | Lock-файлы, Docker, seed, backup/restore, команды проверок | Проверено на Windows/Docker/Chrome; Safari не проверен |

## Что оставалось после версии 1.2

Миграции, управление аккаунтом, общий лимит и локальное резервирование реализованы в исходниках 1.3. Актуальное разделение реализованного, развёрнутого и внешних зависимостей — [отчёт 1.3](11-Технический-долг-1.3.md). Ниже сохранён исходный список аудита.

1. Настроить реальную почту и согласовать режим подтверждения для финальной сдачи.
2. Получить контракт и доступ к официальному ФСП ID/реестру; заменить демонстрационный адаптер.
3. Провести независимую экспертную оценку заданий каждого направления. Нынешние вопросы проверяют ограниченный набор основ; восемь ответов не доказывают весь профессиональный грейд.
4. Собрать релевантность от работодателей, независимый test, проверить сегменты и результаты реального найма. Текущая обученная модель — рабочий синтетический baseline.
5. Настроить постоянный домен/сервер, SMTP, централизованный мониторинг, внешние резервные копии, миграции схемы и процедуру удаления аккаунтов.
6. Перед несколькими API-репликами вынести rate limiter из памяти в общее хранилище. Для большого банка добавить retrieval до ранжирования и индексы навыков. Репликация, очереди и SLA пока не реализованы.

Эти пункты нельзя закрыть одной сменой оформления или увеличением числа синтетических записей. Они не скрыты за статусом «готово».
