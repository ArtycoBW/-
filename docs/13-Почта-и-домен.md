# Отправка почты для постоянного домена

Состояние на 11 октября 2026 года: версия 1.3 развёрнута в отдельном проекте
`razryad-domain`; приложение доступно локально через порт 3001. Исходный сайт
через QuickTunnel и оба контейнера туннелей не перезапускались.

## Почта

- Отправитель: `Разряд <noreply@agropulseai.ru>`.
- SMTP: `smtp.timeweb.ru`, порт 587, STARTTLS с проверкой сертификата и имени сервера.
- Авторизация: полный адрес ящика и пароль из приватного `.local/domain-api.env`.
- Пароль не хранится в репозитории. Не публиковать вывод `docker inspect` с окружением
  или `docker compose config`, содержащий значения секретов.
- Тестовое письмо принято SMTP-сервером; владелец подтвердил получение во входящих
  Gmail. Также проверен защищённый вход IMAP для автоматического сквозного теста.

Публичный DNS на момент проверки содержит MX Timeweb, SPF с `include:_spf.timeweb.ru`
и DKIM в `dkim._domainkey.agropulseai.ru`. При переходе на Cloudflare нужно проверить
наличие этих записей в новой зоне. Автоматическое сканирование зоны до создания
ящика могло не включить новый DKIM.

Настройки провайдера: https://timeweb.cloud/docs/mail/email-clients-configuration

## Что остаётся до включения подтверждений

На момент проверки Google DNS и Cloudflare DNS возвращают NS Timeweb для
`agropulseai.ru` и NXDOMAIN для `razryad.agropulseai.ru`. Прямая проверка
авторитетных NS из текущего окружения завершилась тайм-аутом, поэтому состояние
зоны Cloudflare отдельно не подтверждено.

В рабочем окружении пока сохранены:

```dotenv
PUBLIC_ORIGIN=https://razryad.agropulseai.ru
COOKIE_SECURE=true
EMAIL_VERIFICATION_REQUIRED=false
PASSWORD_RECOVERY_ENABLED=false
EXPOSE_DEMO_MAIL=false
```

После появления публичного HTTPS и подтверждения доставки тестового письма:

1. Проверить MX, SPF и DKIM на действующих NS, открыть сайт по публичному адресу.
2. В приватном окружении доменного API включить `EMAIL_VERIFICATION_REQUIRED=true`
   и `PASSWORD_RECOVERY_ENABLED=true`.
3. Пересоздать только доменный API:
   `docker compose --env-file .local/domain.env -f compose.domain.yml up -d --no-deps domain-api`.
4. Проверить регистрацию, одноразовую ссылку подтверждения, вход и восстановление.
   Ссылка действует один час. Числовой код в текущем интерфейсе не используется.

При недоставке писем вернуть оба флага в `false` и применить ту же команду.
Не выполнять `compose down` и не перезапускать туннели.

Обновление SMTP проверено шестью тестами авторизации, включая отказ при недоверенном
сертификате до передачи логина и пароля. Перед развёртыванием 1.3 выполнено
восстановление резервной копии с 485 пользователями; миграция — `002_operations`.

## Автономная проверка и завершение запуска

В текущем чате Codex включена проверка каждые 30 минут. Она работает при запущенных
ПК, Codex, Docker и доступном интернете. Неизменное ожидание DNS не требует
повторных уведомлений. Ссылки уже поданной заявки остаются прежними.

`python scripts/domain-release.py` выполняет только чтение: два публичных DNS,
MX/SPF/DKIM, сертификат HTTPS, HTML, API/БД и прежний публичный адрес. Код выхода
2 означает отсутствие готовности; 0 — успешную проверку. Результат сохраняется
в `.local/domain-release/preflight.json`. Сам скрипт не меняет Docker или DNS.

Порядок для оператора автоматизации после успешной проверки:

1. Сохранить приватную копию `.local/domain-api.env` и список ID/StartedAt
   старых контейнеров и обоих туннелей. Проверить последнюю резервную копию БД.
2. Включить два почтовых флага из предыдущего раздела. `EXPOSE_DEMO_MAIL=false`
   и `COOKIE_SECURE=true` сохранить. Пересоздать только `domain-api` командой выше.
3. Дождаться `/ready`, открыть регистрацию в браузере и выполнить
   `python scripts/domain-release.py --verify-mail`. Тест регистрирует собственный
   неопубликованный профиль с адресом нашего ящика, читает только новые письма
   этого теста через IMAP и проверяет подтверждение, cookies, вход, сброс пароля,
   отзыв сессий, повторное использование ссылок. Затем удаляет свой профиль.
4. Если тест прервался, файл `.local/domain-release/test-account.json` содержит
   доказательство владения и приватные данные только тестового профиля. Не удалять
   этот маркер и не повторять регистрацию вслепую. Сначала выяснить, создан ли
   профиль, сверить случайное имя и ID; удалять разрешено исключительно этот
   тестовый профиль. Существующий профиль с таким email трогать нельзя.
5. При неуспехе восстановить предыдущие значения флагов и пересоздать только
   `domain-api`; проверить старый сайт. Сохранить локальную причину для исправления.
6. После успешного теста и проверки браузерного интерфейса выполнить
   `python scripts/domain-release.py --notify`. Пользователь разрешил одно итоговое
   письмо на свой адрес с постоянной ссылкой. Скрипт повторяет проверку доступности
   и требует результат E2E не старше часа. `notification.json` блокирует повторную
   отправку даже при прерывании SMTP; состояние `pending` нужно проверить вручную.
7. Зафиксировать результат, сравнить защищённые контейнеры с исходным списком и
   завершить автоматизацию. До реального успеха не сообщать о готовности сайта.

Локальные проверки защит скрипта: `python scripts/test_domain_release.py`.
